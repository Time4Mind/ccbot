# Multi-node ccbot - TODO и контракт разработки

Статус: черновик для согласования и последующей реализации агентами.

Базовый эталон: commit `5f8ddaa` (`main`). Ветка разработки:
`feature/multi-node-runtime`.

## 1. Подтверждённая цель

- Один ccbot-лидер работает на основном компьютере и единственный получает
  Telegram updates.
- Используется один существующий Telegram-бот. На дополнительных машинах не
  создаются и не запускаются отдельные Telegram-боты.
- Пользователь может выбрать ноду и управлять через лидера сессиями на этой
  машине.
- Нодой может быть любая платформа, уже поддерживаемая ccbot. Расширение списка
  поддерживаемых платформ в этот проект не входит.
- Текущая локальная работа на одной машине является эталоном и не должна
  деградировать по функциям, скорости реакции или надёжности.

## 2. Обязательный UX-gate

До реализации пользовательского поведения необходимо согласовать с Артёмом
все пользовательские flow из раздела 6. Согласование проводится наглядно:

1. текущий flow;
2. предлагаемый flow по шагам;
3. состояния UI и точные кнопки/тексты;
4. ошибки, offline и возврат назад;
5. acceptance-сценарий, который Артём сможет проверить в Telegram.

Формат согласования - компактная таблица. Текстовое описание без состояний и
переходов не считается согласованием. Если в ходе реализации обнаружен новый
пользовательский сценарий, работа по нему останавливается до отдельного
согласования. Агент не должен самостоятельно выбирать расположение кнопок,
автопереход, fallback, очередь, уведомление или поведение при ошибке.

Техническое исследование, тестовые fixtures и невидимый пользователю рефакторинг
разрешены до UX-gate только при доказанном сохранении текущего поведения.

## 3. Предлагаемая архитектура - пока не согласована

```text
Telegram
   |
ccbot leader
   - единственный bot token и polling
   - Telegram UI и карточки
   - канонический список нод и сессий
   - маршрутизация команд и событий
   |
   +-- LocalNodeRuntime -> локальный tmux -> Claude/Codex
   |
   +-- RemoteNodeRuntime -> node-agent -> tmux -> Claude/Codex
   |
   +-- RemoteNodeRuntime -> node-agent -> tmux -> Claude/Codex
```

Worker/node-agent запускается из того же проекта, но не знает Telegram token и
не обращается к Telegram API. Он предоставляет только ограниченный node API.
Универсальный remote shell в API запрещён.

Рекомендуемый транспорт для целевой реализации - постоянное двунаправленное
соединение с авторизацией и push-событиями. SSH-вызовы допустимы для прототипа,
но не должны становиться вторым независимым production-путём.

## 4. Черновая модель данных

Добавить сущность `Node`:

- `id` - стабильный короткий идентификатор, не hostname;
- `display_name` - пользовательское имя;
- `platform` и `arch`;
- `endpoint` или параметры выбранного транспорта;
- `capabilities` - реально доступные функции и backend;
- `protocol_version` и `ccbot_version`;
- `last_seen_at`, health и причина недоступности;
- pairing/auth metadata без хранения секретов в tracked-файлах.

Добавить `node_id` в `Session`, `WindowState`, monitor offsets и все связи с
tmux. Локальный `window_id` не глобален: `@5` на двух машинах - разные окна.
Ключ исполнения должен быть составным: `(node_id, window_id)`.

Leader хранит канонические пользовательские настройки, выбранную ноду,
Telegram carrier/card state и глобальный список сессий. Worker хранит
локальную execution truth: tmux, agent process, transcript и локальные файлы.

Перенос живой сессии или transcript между нодами не входит в исходный scope.
Переключение ноды означает смену области управления, а не миграцию процесса.

## 5. Черновой node API

Минимальные операции:

- handshake, capabilities, health и version compatibility;
- список доступных backend и проверка авторизации;
- browse/create directory;
- create/resume/stop/close session;
- send text, key и подтверждение интерактивного prompt;
- capture terminal state и screenshot source;
- stream нормализованных transcript/status events;
- read history/archive pages;
- upload входящего Telegram-файла на целевую ноду;
- download результата с целевой ноды через leader;
- model/effort picker state;
- usage/quota, если backend предоставляет это на ноде.

Каждая изменяющая команда получает уникальный request ID. Повтор после разрыва
не должен повторно создать сессию, отправить prompt или закрыть окно. Worker
подтверждает приём и итог отдельно. После reconnect стороны сверяют event
sequence и передают пропущенные события без дублей.

## 6. Реестр пользовательских flow для обязательного согласования

Статус всех строк ниже: **не согласовано**, пока Артём явно не подтвердил
конкретную таблицу flow.

| ID | Flow | Вопросы, которые надо решить до реализации |
|---|---|---|
| UF-01 | Просмотр списка нод | Где находится вход, что видно по каждой ноде, как показываются online/offline и backend |
| UF-02 | Переключение ноды | Какая карточка открывается, сохраняется ли последняя сессия каждой ноды, что происходит при offline |
| UF-03 | Список сессий | Показывать только выбранную ноду или все ноды, как подписывать источник, как работает циклическая пагинация |
| UF-04 | Создание сессии | Порядок node -> backend -> directory, условия пропуска шага, Back/Cancel на каждом экране |
| UF-05 | Default-сессия | На какой ноде держать резерв, что происходит при смене default-ноды и offline |
| UF-06 | Отправка prompt | Момент привязки к node/session, UI ожидания, поведение при разрыве до и после ack |
| UF-07 | Очередь offline | Запрещать отправку, хранить очередь или спрашивать пользователя; TTL и отмена |
| UF-08 | Переключение во время работы | Что остаётся в фоне, какие карточки обновляются, как не вернуть пользователя назад |
| UF-09 | Фоновые уведомления | Какие состояния присылаются с другой ноды и как подписывается источник без флуда |
| UF-10 | Stop/Close | Поведение при сетевой неопределённости, повторный тап, архивирование и fallback активной сессии |
| UF-11 | Archive/Restore | Доступность при offline, выбор ноды восстановления, отсутствие transcript на исходной ноде |
| UF-12 | Directory browser | Удалённые пути, Home, создание папки, Back, ошибки прав и исчезновение директории |
| UF-13 | Фото/файлы/forward | Где виден upload, когда prompt считается принятым, ошибки передачи и повтор |
| UF-14 | Скачивание файлов | Как leader получает файл с worker, лимиты, истёкший файл и кнопка формата |
| UF-15 | Voice/preprocessing | Где выполняются STT и preprocessing, строгая фиксация целевой node/session |
| UF-16 | Screenshot/rich media | Кэш на ноде или лидере, offline/устаревший кадр, индикатор работы агента |
| UF-17 | Terminal option | Что означает терминал удалённой ноды и поддерживается ли внешний attach |
| UF-18 | Model/effort picker | Node/backend capabilities, Back/Esc, смена модели во время работы |
| UF-19 | Approvals/questions | Доставка вопроса с ноды, автоапрув, потеря соединения, sticky error state |
| UF-20 | Node pairing | Добавление, подтверждение fingerprint, rename, revoke и удаление ноды |
| UF-21 | Leader restart | Восстановление выбранной ноды, карточек, очередей и непрочитанных статусов |
| UF-22 | Worker restart/reconnect | Видимое состояние, восстановление tmux/session binding и пропущенных событий |
| UF-23 | Несовместимая версия | Текст ошибки, допустимый read-only режим и порядок обновления |
| UF-24 | Удаление ноды | Что делать с живыми и архивными сессиями и как исключить случайную потерю данных |

Любой новый callback или экран должен ссылаться на согласованный `UF-*` в PR.

## 7. Нефункциональные требования

### Производительность

- Локальный путь не должен получать сетевой round-trip и не должен становиться
  медленнее текущего baseline.
- Worker отправляет изменения push-моделью. Leader не опрашивает каждую ноду с
  текущими короткими интервалами card/status polling.
- Heartbeat в покое редкий и дешёвый; частота согласуется после измерения.
- Screenshot и история передаются по запросу или при реальном изменении, а не
  непрерывно.
- Не реплицировать полные transcript на leader по умолчанию: это удваивает
  запись на диск. Offline-доступ к архиву требует отдельного решения и замера.

### Надёжность

- Сетевой timeout не равен отказу команды. До retry нужно проверить receipt.
- Доставка prompt не может перейти на другую node/session после приёма.
- После reconnect не допускаются пропуск, дубль или перестановка событий.
- Падение leader не останавливает уже запущенные agent processes на worker.
- Worker не может стать вторым Telegram poller.

### Безопасность

- Bot token существует только на leader.
- Pairing использует явное подтверждение и отзыв credentials.
- Node API содержит allowlist типизированных операций, а не shell endpoint.
- Секреты не попадают в Git, state dump, логи и Telegram-карточки.
- Рекомендуемая сеть - Tailscale/WireGuard или эквивалентный приватный контур
  плюс прикладная взаимная авторизация.

### Совместимость

- Старый `state.json` без `node_id` мигрируется в `local` без потери сессий.
- Один локальный leader после миграции ведёт себя визуально и функционально как
  commit `5f8ddaa`.
- macOS, Linux arm64 и поддержанный chroot/proot сохраняют текущие ограничения;
  multi-node не добавляет новые платформенные обещания.

## 8. План реализации после согласования flow

### Wave 0 - baseline и контракты

- [ ] Снять baseline latency/CPU/RAM/write для локальной работы.
- [ ] Зафиксировать текущие e2e-flow single-node тестами.
- [ ] Утвердить все применимые `UF-*` с Артёмом.
- [ ] Утвердить threat model и транспорт.
- [ ] Утвердить protocol schema и правила совместимости версий.

Gate: ни один пользовательский flow не остаётся со статусом «решить по ходу».

### Wave 1 - локальная абстракция без изменения поведения

- [ ] Ввести `NodeRuntime` protocol.
- [ ] Реализовать `LocalNodeRuntime` поверх существующих tmux/transcript/files.
- [ ] Добавить `node_id=local` и обратимо мигрировать state.
- [ ] Перевести прямые вызовы tmux на runtime по зонам, небольшими коммитами.
- [ ] На каждом коммите сравнивать Telegram output и latency с baseline.

Gate: полный suite и live single-node acceptance; визуально поведение не
изменилось, latency тапов не выросла.

### Wave 2 - node-agent и transport

- [ ] Добавить отдельный режим запуска node-agent без Telegram token.
- [ ] Реализовать pairing, auth, capabilities и version handshake.
- [ ] Реализовать idempotent commands, ack/result и event sequence replay.
- [ ] Добавить reconnect, bounded buffers и health.
- [ ] Тестировать disconnect на каждой границе request/ack/result.

Gate: синтетический leader управляет worker без Telegram и без дублей после
принудительных разрывов.

### Wave 3 - согласованный Telegram core

- [ ] Реализовать только подтверждённые UF для списка/выбора нод.
- [ ] Создание, ввод, stop/close и switcher через выбранный runtime.
- [ ] Directory browser и default-сессия.
- [ ] События, карточки и фоновые статусы с нескольких нод.

Gate: живой сценарий local + одна remote-нода проходит утверждённую таблицу
переходов; запросы строго принадлежат выбранной сессии.

### Wave 4 - функциональный паритет

- [ ] Archive/restore и история.
- [ ] Фото, документы, download buttons и forwarded media.
- [ ] Voice и preprocessing.
- [ ] Screenshot/rich media/terminal.
- [ ] Model/effort, approvals и usage.
- [ ] Naming, cleanup, rotation и уведомления.

Gate: матрица существующих функций проходит отдельно на local и remote node.

### Wave 5 - эксплуатация и release

- [ ] Installer/service definitions для node-agent на уже поддержанных ОС.
- [ ] Обновление leader/worker с version gate и rollback.
- [ ] Метрики reconnect, command latency, queue depth, event lag и traffic.
- [ ] Документация pairing/revoke/recovery.
- [ ] Пятиминутный load audit и restart/network-partition smoke.

Gate: rollback не повреждает single-node state, worker sessions продолжают
работать при рестарте leader, а повторное подключение не дублирует события.

## 9. Предварительная оценка

- SSH/core prototype: 6-10 рабочих дней.
- Целевой MVP с reconnect, директориями, историей и screenshots: 10-15 дней.
- Полный паритет текущего ccbot: 15-25 рабочих дней.
- Ориентир объёма полного решения: 3-5 тыс. строк production-кода и 2-4 тыс.
  строк тестов.

Оценка уточняется после UX-gate и protocol spike. Она не включает перенос
сессий между нодами, HA/election нескольких лидеров и поддержку новых ОС.

## 10. Правила работы агентов

- Каждый агент получает один task contract с непересекающейся зоной файлов.
- Task contract обязан перечислять относящиеся к задаче согласованные `UF-*`.
- Если нужный `UF-*` не согласован, агент делает только read-only исследование
  и возвращает варианты, не пишет production UI/behavior.
- Не менять Telegram-тексты, расположение кнопок, fallback и автоматические
  переходы без явного approved flow.
- Сначала публичный regression test, затем минимальный vertical fix.
- Не объявлять готовность по unit-тесту: нужен original-path probe и физический
  runtime receipt.
- Не смешивать node refactor с посторонними улучшениями текущего ccbot.
- Один owner синтезирует изменения и проверяет cross-node ordering/security.
- Commit -> локальный deploy -> подтверждение Артёма -> push/merge.
- Если в течение 10 минут после deploy нет ответа Артёма, deploy откатывается.

## 11. Definition of Done

- Все реализованные пользовательские flow заранее согласованы и имеют живые
  acceptance-пробы.
- Один Telegram leader одновременно управляет local и remote sessions Claude и
  Codex без второго bot token.
- Переключение ноды не переносит и не перепривязывает принятый prompt.
- Network partition/reconnect не теряет и не дублирует команды и события.
- Single-node режим не отличается от baseline `5f8ddaa` и не медленнее его.
- CPU/RAM/network/disk измерены в покое и под нагрузкой; постоянного частого
  polling и полной transcript-репликации нет.
- Upgrade, restart, revoke и rollback проверены на поддержанных целевых средах.
